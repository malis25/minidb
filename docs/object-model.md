# Object Model and Indexes

MiniDB stores JSON objects. Each object receives a database-owned unsigned
64-bit integer ID. IDs begin at zero and increase by one for each successful
create. The application does not send a database ID when creating an object;
the server returns it.

## JSON object values

Any top-level field can contain a JSON string, integer, floating-point
number, boolean, null, array, or nested object:

```json
{
  "id": "app-user-9",
  "username": "ada",
  "email": "ada@example.test",
  "age": 36,
  "rating": 4.75,
  "active": true,
  "middle_name": null,
  "friends": [12, 18],
  "profile": {
    "city": "London"
  }
}
```

Objects may be nested up to 128 levels. The same limit applies to arrays and
objects inside stored property values.

Each persistent database has a schema in its manifest. Schemas specify
`properties`, each property's type, and a `required` property-name list.
Supported types are `string`, `integer`, `number`, `boolean`, `null`, `object`,
and `array`; nested object schemas have their own `properties` and `required`,
and arrays have an `items` schema. Undeclared fields are rejected. A schema
change is accepted only if all existing objects pass the new schema.

The object's `"id"` field above is ordinary application data. It is not the
database ID. If this object is created when the database next ID is `0`, the
database key is `0`, while the field value remains `"app-user-9"`.

## Numeric database IDs

IDs are `std::uint64_t` values generated by `Database::create`. They start at
zero, remain monotonic across deletes and server restarts, and are not reused.
The manifest persists the next ID. Updating or deleting an object requires its
numeric database ID. A client must retain the `id` returned by create if it
will later update or remove that object.

## C++ API

```cpp
#include "minidb/database.h"

minidb::Database database;
minidb::Object user = {
    {"username", "ada"},
    {"email", "ada@example.test"},
    {"friends", {12, 18}},
    {"profile", {{"active", true}, {"rating", 4.75}}},
};

const std::uint64_t user_id = database.create(std::move(user));
const auto found = database.get(user_id);
if (found) {
    const auto& username = found->at("username");
}

const auto matches = database.find("email", "ada@example.test");
```

`create` returns the assigned ID. `set(id, object)` replaces an existing
object without changing its ID; it throws if the ID does not exist. `get`
returns an immutable shared object snapshot or an empty pointer. `remove`
returns whether an object existed. `find(field, value)` returns all matches,
sorted by ID.

The default `Database` is in-memory only. To persist it, pass a storage
implementation such as `SegmentedStorage` when constructing it; the server
does this from per-database metadata. The `maximum_objects_per_segment` limit
counts IDs first created in each segment. Updates and deletes do not consume
the quota.

## Equality indexes

The database maintains a secondary hash index for every **top-level** object
property. The index key consists of the property name and the JSON
serialization of its value. This supports exact equality lookups for strings,
numbers, booleans, null, arrays, and nested objects. JSON types remain distinct:
integer `1`, floating-point `1.0`, string `"1"`, and boolean `true` do not
share an index entry. Object properties are canonically ordered by the JSON
library before serialization, allowing equivalent nested objects to compare.

Example query:

```cpp
const auto matches = database.find("username", "ada");
```

An object with an `email` property can be returned by
`find("email", "ada@example.test")`. If several objects have that value, all
are returned. Updating an object removes its old property index entries and
adds entries for the replacement. Deletion removes its entries.

Fields inside a nested object are not independently indexed in this version.
For example, `profile.city` is data inside the top-level `profile` value and
cannot yet be queried as the field name `"city"`. Arrays are indexed as whole
values, not as separate values for each array element. Range comparisons,
partial text matching, and multi-condition expressions are not implemented.

## Complexity and tradeoffs

The ID map and exact-value indexes are `std::unordered_map` structures:

- ID lookup: average O(1) by object count. Create, replacement, and deletion
  also maintain the secondary indexes, taking O(p) index updates for an object
  with `p` top-level properties, plus the value serialization costs.
- Indexed equality lookup: average O(1) to find a posting set, then O(k) to
  return the `k` matching objects.
- Full ID listing and unpaged result ordering: O(n log n) or O(k log k),
  respectively. Paginated HTTP listing selects the requested prefix with
  expected O(n) selection plus sorting of that prefix, while still collecting
  all IDs in temporary memory.
- Index maintenance: O(p) index updates per write, where `p` is the number of
  top-level properties, plus the cost to serialize indexed values.

Indexing every property makes common equality queries fast without requiring
the caller to declare indexes, but increases RAM usage and write cost. The
current database keeps every live object in memory, in addition to the index.
